You are distilling reusable knowledge from historical PRs.

Given a PR description, patch, and time mapping context, output a raw JSON list of knowledge items. Each item must contain:
- file
- function
- keywords
- rationale

Primary objective:
- Maximize downstream retrieval usefulness.
- Prefer higher granularity when evidence supports it: function-level > module/file-level > miss.
- Reduce parse_empty and zero-item outputs.
- Keep the output compatible with strict JSON array parsing.

Core guidance:
1. Ground every item in concrete code evidence from the diff.
   - Use the patch as the main source of truth; use PR text only to disambiguate behavior when the code evidence is clear.
   - Prefer production-code changes over templates, labels, changelog text, fixtures, and test-only edits.
   - Treat incidental edits as noise unless they clearly affect runtime behavior or implementation.
   - If evidence is weak, indirect, or purely incidental, omit the item rather than guessing.

2. Choose the narrowest valid scope.
   - Emit a function-level item when a specific function or method is clearly implicated by the change.
   - Emit a module/file-level item only when the change spans multiple functions or reflects a broader implementation pattern.
   - Avoid collapsing distinct changes into one broad item if they can be separated.
   - If function-level evidence is uncertain, prefer a file/module item over an invented function guess.

3. Write high-signal keywords.
   - Prefer searchable, specific terms tied to behavior, domain concepts, state transitions, validation, error handling, inputs/outputs, data flow, or externally visible effects.
   - Include concrete technical concepts that would help retrieval match similar future changes.
   - Avoid generic or low-information keywords such as bug_fix, update, refactor, cleanup, test, or miscellaneous.
   - Do not overstuff keywords; keep them focused and relevant.
   - Favor keywords that describe behavior and mechanism rather than names or surface syntax.

4. Make rationales concise and evidence-based.
   - State what changed and why it matters in generalizable terms.
   - Reference the code behavior at a high level without inventing details.
   - Do not mention repository-specific identifiers or sample-specific context.
   - Keep rationales short but specific enough to support retrieval.

5. Filter noise aggressively, but not so aggressively that useful items are lost.
   - Ignore formatting-only edits, whitespace changes, generated files, temporary scaffolding, and non-production artifacts unless they directly affect behavior.
   - Ignore isolated test additions unless the production code change is the primary knowledge source.
   - Prefer behavior-changing or implementation-shaping changes.
   - When a diff contains some noisy edits and some real behavior changes, extract only the real knowledge-bearing portion.

6. Be conservative with inference.
   - If the diff suggests a likely intent but does not make it clear, do not fabricate specificity.
   - If a file-level item is the best supported output, use it rather than forcing a function-level guess.
   - If a change only supports a broad pattern, express that pattern without naming concrete internal identifiers.
   - If no reliable knowledge can be extracted, return an empty JSON list rather than malformed output.

7. JSON robustness requirements.
   - Return only a raw JSON array.
   - Do not include commentary, code fences, or extra text.
   - Ensure valid JSON syntax.
   - Use consistent field types across items.
   - Keep strings clean and parseable.

Suggested output style:
- One array element per distinct knowledge item.
- Prefer a small number of strong items over many weak ones.
- When multiple items are justified, separate them by scope or behavior.
- Aim for useful retrieval density, not verbosity.
- Prefer non-empty output when there is any clear behavior change, but never at the expense of inventing unsupported knowledge.
