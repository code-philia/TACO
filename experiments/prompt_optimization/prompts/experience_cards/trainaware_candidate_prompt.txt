Extract reusable knowledge that may help locate relevant code for future similar issues.

Focus on information that is supported by the code patch. Use the PR text as context, but do not rely on it when it conflicts with the patch.

Return only a valid JSON array. Each item must have:

- function: the most relevant function or method if clear; otherwise use "FILE_SUMMARY"
- keywords: a short list of useful retrieval keywords
- rationale: a concise explanation of the reusable behavior or implementation knowledge

Prefer specific, code-grounded knowledge over generic summaries. Do not include commentary outside the JSON array.

Learned general experience:
1. Prefer patch-backed behavior over narrative phrasing: When distilling a PR, anchor each card in an explicit code change or added test behavior, and down-rank wording from the PR description if the patch does not confirm it.
2. Capture the reusable hook, guard, or parameterized path: Extract the specific implementation pattern that was introduced or adjusted, such as a new hook method, a conditional guard, a configurable attribute, or a shared helper path, rather than restating the feature at a high level.
3. Use retrieval keywords that reflect code shape and data flow: Include concise keywords for the affected behavior, the kind of object or argument being handled, and the operation performed, especially terms that describe transformation, filtering, delegation, or context assembly.
4. Name the concrete code mechanism, not the product intent: When a PR mostly describes a feature, distill the implementation mechanism actually changed in the patch: the guard added, default overridden, context field inserted, iterator materialized, helper called, or lookup path rewritten. Avoid summarizing the user-facing goal unless it is directly reflected in the code.
5. Add retrieval cues for where the changed logic lives in the call flow: For each card, include keywords that describe the code location by role in the flow, such as entrypoint, wrapper, parser, validator, view context builder, request merger, or build manifest, together with the data being transformed or passed through.
