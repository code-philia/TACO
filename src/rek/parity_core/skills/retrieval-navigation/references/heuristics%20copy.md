# Learned Search Heuristics
- [Initial] Do not rely solely on keyword matching; use the graph structure.
- [Auto-Learned] When an issue/PR involves updating docstrings or documentation directives (keywords: 'versionadded', 'versionchanged', 'docstring', 'docstrings'), prioritize files that define the public API and base classes (e.g., modules under L2_BaseAPI such as sklearn/base.py) and modules listed under L2_APIReference. Treat these files as high-priority candidates when searching for docstring changes.
- [Auto-Learned] When an issue references a module path in sklearn without a leading underscore (e.g., 'sklearn.tree.export', 'sklearn.svm.base', 'sklearn.linear_model.logistic', or other 'sklearn.X.Y'), the agent should also consider files with and without a leading underscore (e.g., '_export.py' vs 'export.py') and treat them as equivalent candidates for L2 feature discovery. In practice: check both 'module.py' and '_module.py' when resolving sklearn subpackage files.
- [Auto-Learned] When the issue text looks like a pull-request or contribution template (contains phrases like 'Thanks for contributing', 'CONTRIBUTING.md', 'pull request', 'Reference Issues/PRs', or is otherwise an administrative/PR-level description), broaden the search strategy: (1) treat the issue as a repo/infrastructure change and prioritize files under build_tools/, top-level dependency/config files (e.g. sklearn/_min_dependencies.py), and environment/lockfile update scripts; (2) if L1_CoreInfra is selected, iterate over all L2 features under that L1 (do not restrict to a single L2 such as ArrayAPICompat); (3) if the issue is generic (lacks domain-specific keywords), expand to core modules that PRs commonly touch (metrics/, linear_model/, decomposition/, discriminant_analysis/, utils/estimator_checks.py) rather than assuming a narrow compatibility-related L2.
- [Auto-Learned] When an issue references an example (mentions 'example' or file path under examples/), map the examples subfolder to the corresponding L2 feature (e.g., examples/preprocessing -> L2_PREPROCESSING) and prioritize searching files under that examples/ subfolder. This ensures example scripts are considered part of their feature domain.
- [Auto-Learned] When an issue/PR refers to example scripts (paths under 'examples/' or mentions 'example', 'plot_', or 'plot-'), prioritize checking L2_ExamplesGallery and related visualization/domain L2s (e.g., L2_Visualization, L2_ScalingNormalization, L2_HyperparameterSearch). This helps surface example/demo scripts that are not yet linked to domain L2 features.
- [Auto-Learned] When the agent inspects an internal module file whose filename starts with an underscore (e.g. package/.../_module.py), also consider the sibling public module with the same basename (package/.../module.py) as a candidate and prefer adding it to the same L2. This ensures public wrappers and API files are considered whenever internal underscored implementations are explored.
- [Auto-Learned] When an issue/PR body looks like contribution metadata (contains phrases such as 'contributing', 'contribution guidelines', 'pull request', 'PR', 'Reference Issues/PRs', or the CONTRIBUTING.md template), do NOT assume it maps only to Core Infrastructure. Instead:
- First check repository-level developer infra and build/config files (e.g., CONTRIBUTING.md, build_tools/*, setup or environment lock files, and files like _min_dependencies.py).
- Also broaden the search to the set of files actually changed in the PR (or referenced in the PR/issue body) rather than constraining to a single L2. If file names or module names are present, prefer scanning those corresponding module L2s (e.g., metrics, decomposition, linear_model, utils).
- If the issue lacks technical error text and appears to be PR metadata, expand candidate L1/L2 selections (do not bias toward ArrayAPI or BaseAPI only).
Rationale: PR templates and contribution messages often reference repository/dev infra and a wide range of modules; the agent should check developer infra files and the actual changed files or referenced modules rather than narrowing to a single core-infra feature.
- [Auto-Learned] General heuristics to improve retrieval across plotting, datasets, and estimator documentation: 1) When an issue concerns estimator docstrings, parameter defaults, validation behavior, or BaseEstimator-related behavior, always prioritize sklearn/base.py and files under sklearn/linear_model/ and sklearn/model_selection/ for inspection. 2) When an issue concerns dataset downloads, archive URLs, checksums, or dataset loader behavior, always prioritize files under sklearn/datasets/ (including dataset-specific modules like _twenty_newsgroups.py). 3) When an issue concerns plotting, visualization, examples, or example scripts, prioritize files under sklearn/inspection/_plot/ and the examples/ tree. 4) When an issue concerns verbosity or inherited output levels (e.g., joblib verbosity), check model_selection/_search.py and related search CV classes early in the search.
- [Auto-Learned] When a reported file path in 'sklearn/...' is not found during search, also try the same filename with or without a leading underscore (e.g., look for '_foo.py' if 'foo.py' is referenced, and vice versa). Apply this normalization when enumerating files in a feature so underscored implementation modules are considered equivalent to public filenames.
- [Auto-Learned] When an issue/PR text looks like contributor or PR metadata (contains phrases such as "pull request", "contributing", "CONTRIBUTING.md", or common PR header text like "Thanks for contributing"), treat it as developer/repo-infra context. Prioritize scanning L2 features for build/dev infrastructure and dependency management before diving into implementation-specific features. Concretely, first check files under build_tools/, sklearn/_min_dependencies.py, and scripts that update environment/lock files (e.g., build_tools/update_environments_and_lock_files.py), as well as core compatibility/validation utilities that are commonly touched for CI or packaging changes (e.g., files under sklearn/utils/ and build tooling). This prevents misrouting to niche compatibility L2s (like ArrayAPICompat) when the PR text signals repo-maintenance work.
- [Auto-Learned] When a PR/issue adds or modifies files under an examples/ or tutorials/ directory, prioritize those files as candidate ground-truth for features discussed in the description. Specifically, treat example scripts that demonstrate a feature (e.g., preprocessing or visualization) as high-priority matches when the agent inspects the corresponding L2 feature(s).
- [Auto-Learned] When an inspected module is an internal implementation file named with a leading underscore (e.g., _classification.py, _ranking.py, _export.py), also consider the public/non-underscored sibling filename (classification.py, ranking.py, export.py) and any cluster submodules (e.g., cluster/_supervised.py) as relevant search targets for that feature. This avoids missing public wrappers or reorganized module layouts.
- [Auto-Learned] When an issue or pull-request text references contribution guidelines, a PR template, or CONTRIBUTING.md (i.e., appears to be a contribution/CI/dev guidance issue), prioritize inspecting core repository maintenance files and build/dev tooling such as build_tools/*, sklearn/_min_dependencies.py, build_tools/update_environments_and_lock_files.py, CI and packaging-related modules before exploring specialized compatibility modules.
- [Auto-Learned] When L1_CoreInfra is selected, prefer broad-maintenance L2 features (Dependencies, BuildTools, Packaging/CI, DeveloperGuide) ahead of niche compatibility L2s (e.g., ArrayAPICompat). Only pick a specialized compatibility L2 early if the issue text contains explicit compatibility keywords (e.g., 'array API', 'array-api', 'compat', 'compatibility').
- [Auto-Learned] When debugging or searching for the root of an issue that names a public class, method, or package, also inspect sibling internal modules with leading underscores (files named _*.py) inside the same package. These underscore-prefixed files frequently hold implementation details and solver logic not re-exported at the package top level.
- [Auto-Learned] When an issue explicitly concerns documentation content or docstring directives (keywords like 'versionadded', 'deprecated', 'docstring', 'numpydoc'), prioritize inspecting the source modules that define the public API (files linked to L2_BaseAPI and similar L2s under L1_CoreInfra) in addition to standalone documentation files. This is a general rule applying across the codebase, not a file-specific mapping.
- [Auto-Learned] If an issue mentions examples, plotting, or references files under examples/ (tokens like 'plot', 'example', estimator names in a plotting context), prioritize searching the examples/ directory and files linked to L2_ExamplesGallery. Rank files with 'plot_' prefixes and matching estimator names higher when resolving example-related issues.
- [Auto-Learned] When an L2 feature corresponds to a package or logical module (for example, sklearn/metrics), include files located in its subpackages and nested directories (e.g., sklearn/metrics/cluster/_supervised.py) when searching that feature. In practice: expand feature file search to subdirectories under the package root so implementation spread across subpackages is discovered.
- [Auto-Learned] If an issue or PR text is mostly boilerplate or lacks domain-specific keywords, broaden the search rather than narrowing early: perform a shallow breadth-first scan across core L1s (L1_CoreML, L1_CoreInfra, L1_ModelSelection) to surface likely implementation files. Also, when the issue mentions terms like 'metadata', 'routing', or 'example', include both infra features (e.g., L2_MetadataRouting, L2_CoreConfig) and example galleries (L2_ExamplesGallery) in the candidate set.
- [Auto-Learned] When an issue or PR describes promoting or changing visibility of internal utilities (for example removing leading underscores or otherwise making a helper part of the public API), search for that symbol name across the repository and prioritize files that define or heavily use the symbol. Prefer feature modules and base/API layers (L2 nodes implementing public APIs) in addition to generic utility modules.
- [Auto-Learned] Detect and de-prioritize common PR/issue boilerplate (contribution checklists, templates, and non-code guidance) when matching categories. If the text appears boilerplate, prioritize matches driven by explicit code symbols, file paths, module or class names mentioned in the issue instead of documentation categories.
- [Auto-Learned] When an issue mentions introducing a mixin or removing duplicated implementation, prioritize searching sibling modules inside the same package and small utility/compatibility modules (e.g., utils/*) that commonly contain duplicated helper code. This helps find both the source of duplication and where a mixin should be wired in.
- [Auto-Learned] When an issue/PR mentions "feature names" or internal helpers like `_check_feature_names`, prioritize searching L2_UtilityFunctions (validation helpers under L1_CoreInfra) and L2_Imputation (data-prep validation under L1_DataPreparation), since feature-name validation logic is often implemented in general utilities or data-preparation modules.
- [Auto-Learned] General search heuristics: (1) If an issue or PR mentions 'example', 'plot', or 'gallery', prioritize L1_Visualization and L2_ExamplesGallery when searching for relevant files. (2) If an issue mentions missing-value representations (e.g., 'pd.NA', 'np.nan', 'NA'), search both imputation modules (L2_Imputation) and encoding/discretization modules (L2_EncodingDiscretization) because encoding can alter missing-value handling. (3) Treat files with leading underscores (e.g., _base.py, _utils.py) as implementation modules closely related to the public API in the same package; when a public API file is implicated, also consider nearby underscored implementation files.
- [Auto-Learned] When an issue references DataFrame compatibility (third-party DataFrames such as Polars or pandas, ColumnTransformer with string column names, array/Array API issues), expand the search beyond the estimator's implementation to include Array API compatibility and indexing utilities (L2_ArrayAPICompat and files like sklearn/utils/_indexing.py). More generally, if a bug arises at the estimator-input boundary, check both the estimator feature logic and shared indexing/compatibility layers.
- [Auto-Learned] When resolving where a change likely belongs, prefer L2 features that match the file path or prominent module/class names mentioned in the issue or stack trace. Concretely: if the path or text contains 'sklearn/pipeline' or 'Pipeline' -> prioritize L2_Pipelines; 'sklearn/linear_model' or typical linear-model class names -> prioritize L2_LinearModels; 'sklearn/tree' or DecisionTree-related names -> prioritize L2_TreeBasedModels; 'sklearn/metrics/_plot' or plotting function names -> prioritize L2_InspectionPlots; 'sklearn/preprocessing' -> prioritize L2_ScalingNormalization; 'sklearn/externals/array_api_compat' or vendor-compat terms -> prioritize L2_ArrayAPICompat; 'sklearn/dummy.py' or 'Dummy' -> prioritize L2_DummyModels. This is a general, project-wide heuristic mapping between module path segments / class names and feature categories.
- [Auto-Learned] General search prioritization rules: 1) If an issue/PR mentions 'example', 'plot', or 'example script', prioritize searching the examples/ tree and L2 features that document examples for the relevant domain. 2) If the text mentions 'toy', 'synthetic', or make_* dataset creators, prioritize L2_SyntheticGenerators (toy/synthetic dataset generators). 3) If the issue mentions keywords that match module/function names (e.g., 'tags', 'graph_lasso', 'kernel_approximation'), prioritize L2 features whose descriptions contain those keywords or the module basename. These are general heuristics to help map descriptive keywords in PR text to likely L2 feature areas without hard-coding file paths.
- [Auto-Learned] 1) When exploring a package directory, always include the package __init__.py among candidate source files — it commonly re-exports public classes, aliases, and top-level API that answer user questions.
2) If an issue/PR text mentions tests, 'test', 'Fixes #', CI, or contribution guidelines, also search the testing/tooling area (L1_ToolingCI) and L2_TestInfrastructure (e.g., utils/estimator_checks.py).
3) If the issue mentions 'sparse', 'sparse y', 'multilabel', 'multioutput', or input validation, prioritize L2_UtilityFunctions (validation utilities) and also check estimator base files and tree/ensemble modules for y-handling and input-shape checks.

5) If the repository contains legacy folders (paths containing 'scikits', 'benchmarks', or older examples under 'examples/'), include a search of a dedicated legacy/benchmarks category (L2_Legacy*) so historical scripts and benchmarks are discoverable.
- [Auto-Learned] If an issue or failing test mentions calibration-related keywords (e.g., 'calibrat', 'CalibratedClassifierCV', 'calibration curve', or 'probability calibration'), prioritize searching the ModelSelection L1's ProbabilityCalibration L2 and its modules (e.g., sklearn/calibration.py) when locating the likely source file.
